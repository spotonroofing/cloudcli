# Composer

- Fast mode (ui15 job 17): when Codex is the active provider, the model menu places a `Fast mode` switch directly below Effort with the cost line `1.5x speed, 2.5x usage`; Claude never renders the row. The composer trigger shows a small muted lightning bolt (lucide `Zap`, `h-3 w-3`, `text-muted-foreground`, `data-slot="composer-fast-mark"`) while enabled, sized and inked like the trigger chevron, and nothing when it is off (ui17 job 12); the menu switch row keeps its label and cost line. `codex-fast-mode` is the cloud-synced default for new Codex chats, while `sessions.fast_mode` records an explicit on/off choice for an existing session. Sends pass that boolean to the Codex SDK as `service_tier = "fast"` (or explicit `default` when off); dispatch and maintenance chains force it off.
- Programmatic command sends (ui15 job 21): custom slash commands, the Handoff button, and automatic `/planner` or `/worker` boots submit their expanded tagged command body directly through `useChatComposerState`'s normal send path. The expanded body never enters `input` or the textarea; a typed command clears its own invocation, while button/menu/boot sends preserve any existing user draft. Command wrappers still produce compact transcript bubbles, and boot submissions retain the placeholder-title, boot flag, and hidden-prologue behavior.
- Context window truth (pauseresume job 2): `TokenUsageSummary` is provider-specific. Claude keeps the SDK category breakdown and usable-window treatment unchanged. Codex reads only the newest rollout `token_count.info.last_token_usage` against `model_context_window`; cumulative `total_token_usage` is never a context source. Its expanded popover lists exactly Input from cache, Fresh input, Output, Reasoning, and Context window using the rollout values (fresh input is total input less cached input), and says “No reading yet” before the first token event. The existing sessions filesystem watcher pushes `session_token_usage` over the shared WebSocket on Codex rollout changes, scoped by app session id; the client does not poll.
- Queued-message stack (ui11 phase 1 single card; a stack since ui15 job 2): queueing while messages are already queued appends another card — the cards render in delivery order above the composer (`data-slot="queued-card-shell"` wrapping `QueuedMessageCard`), pushing the transcript up through the `--composer-height` var. Each card edits (pulls its text and attachment descriptors back into the composer) and deletes independently. Storage is the server `queued_messages` table (one row per message, client-generated `id`, `position` append order); every write/claim broadcasts `queued_message_updated` carrying the session's whole ordered stack. Delivery preserves order: the Claude runtime steers the HEAD into a running turn at tool-result boundaries (ui11 phase 2), and end-of-turn flush plus app-level auto-send always claim-pop the head — later messages flush at the following turn ends. Sync clear law (ui15 job 2): the steer's echoed user bubble carries `queuedMessageId`, and the client drops the matching card in that same event (`settleQueuedMessageDelivered`), so card clear and bubble land in one commit — never two round trips; a removed card ramps closed via the shell's grid-rows collapse (0.25s EASE_IN_OUT), never a hard unmount.
- Pane-wide file drop (ui15 job 2): the whole chat pane (`data-slot="chat-pane"`, the `paneRef` div in `ChatInterface`) is the dropzone — dragging a file over the planner or worker pane shows the subtle themed wash (`data-slot="pane-drop-highlight"`: inset dashed `border-primary/40` + `bg-primary/[0.06]` + a small "Drop to attach" chip) and dropping attaches to that pane's composer exactly as a prompt-bar drop; per pane in multi-pane layouts. Project-row drags never trigger it (a drag only paints the pane when its transfer types carry `Files`). The pane owns the drag state itself (ui17 job 6) through `createPaneDragTracker` (`src/components/chat/utils/paneDropHighlight.ts`): a set of entered targets still inside the pane, so the highlight holds from the first dragenter until the last child is left, a drop lands, or a page-level `dragend`/`drop` ends the drag - never blinking off as the pointer crosses nested children. react-dropzone's `isDragActive` is not the source (the pane node reaches both its root ref and `paneRef` through one callback ref, but the highlight reads the tracker). The wash mounts once per drag and fades in on the shared `overlay-enter` ramp, so the entrance never replays mid-drag.
- Prompt history panel (ui15 job 2, `PromptHistoryPanel.tsx`, `data-slot="prompt-history-panel"`): the controls-row history toggle expands the prompt bar area into a panel one third of the pane tall (measured from `data-slot="chat-pane"`, min 180px) via a grid-rows ramp (0.3s EASE_IN_OUT both ways), listing the user's past prompts newest first — this session's and the project's recent conversations, served by `GET /api/prompt-history` (`server/modules/prompt-history/`, which scans the Claude transcript JSONLs of the current session plus up to 10 recent project sessions for real typed prompts — commands, meta rows, and tool results excluded — and parses attachment descriptors back out of the `<files_input>`/`<images_input>` tags). Rows: truncated prompt, paperclip count, time, chevron; expanding shows the full text and downloadable attachment chips (`/api/assets/files/<name>`, the files live on the mini); the hover-revealed Use action (`data-slot="prompt-history-use"`, `touch:opacity-100`) loads the prompt and its descriptors into the composer and closes the panel. Escape closes; fetches show `Skeleton` rows.
- Spellcheck law (ui15 job 2): no browser spell/grammar underline anywhere — `PromptInputTextarea` and the shared `Input` default `spellCheck={false}` + `autoCorrect="off"` (the composer textarea keeps `autoCapitalize="sentences"` for phone dictation), and every raw `<input>`/`<textarea>` (message edit, pasted-text editor, commit boxes, renames, searches, auth fields, cmdk) sets the same explicitly. New text fields must not ship with spellcheck default-on.
- Composer controls (ui16 job 1, amended by ui17 job 9): the bordered prompt enclosure contains the textarea and attachments plus only the prompt-making controls: plus, voice, and send - no clear control lives inside it. A separate full-width row immediately below the enclosure puts the character count flush with the left edge and, on the right, handoff (when available), prompt history, model switcher, then context window. Controls keep the 28px height and icon language; the right group and model label compact at 390px without hiding a control or changing the context popover.
- Two-tap clear at the counter (ui17 job 9, `ComposerClearCounter.tsx`, `data-slot="char-counter"`): the character counter is the clear control, as it was before ui16 job 1. With something to clear, hovering or focusing the counter crossfades the count into the X (`data-slot="composer-clear"`) on the shared `.counter-swap` 0.2s ramp; on the phone the first tap does that reveal. Clearing takes two taps: the first arms the control, swapping the count for a "Tap again to clear" label in place (`data-slot="composer-clear-armed"`, same ramp, monochrome, the button box never resizes); the second tap within `CLEAR_ARM_WINDOW_MS` (2s) clears text and attachments. The arm expires on its own after that window, on a pointer leave, on Escape, and whenever there is nothing left to clear. The undo affordance is unchanged and still replaces the counter for its 4s window (`data-slot="composer-undo-clear"` with the depleting underline).
